# 第一阶段开发任务：语义基础

## 1. 阶段目标

第一阶段只交付所有上层 Runtime 语义需要的底层原语：

```text
validated identifiers
        ↓
dynamic Value + diagnostic Path
        ↓
structured Error
        ↓
Type Contract validation
        ↓
Execution/Correlation context
```

阶段结束时还不能注册或调用 Capability，也不包含 Resource、Task、Observer、
Command 或任何协议 Adapter。这样可避免上层用例在基础语义未稳定前固化错误接口。

## 2. 共同完成标准

每个任务都必须：

- 只引入任务所需的最小公开 API；
- 包含成功、边界和失败行为测试；
- 为公开项提供 rustdoc，并说明重要不变量和错误；
- 保持 safe Rust，不引入协议或第三方序列化类型；
- 通过任务列出的聚焦测试和 `cargo make fast`；
- 不降低已有 lint、覆盖率或检查阈值。

最终阶段候选额外运行 `cargo make full`。只有引入 unsafe、复杂所有权或并发实现时
才需要 `cargo make hardening`；按本阶段设计，正常情况下不应需要 unsafe。

## 3. 有序任务清单

### P1-001：建立 crate 入口与基础模块边界

**目标**：移除 `add` 示例，把 crate 变成可继续构建的 Axiom 语义基础库。

**依赖**：无。

**范围**：

- 在 crate 根补充用途、非目标和模块边界文档；
- 建立最小 `foundation`、`contract`、`execution` 模块入口；
- 暂不创建空的未来模块或公共占位类型。

**验收**：

- crate 不再导出示例 `add`；
- `cargo doc --no-deps` 可生成无警告文档；
- 公开模块职责与整体规划一致。

**测试与验证**：`cargo test --all-targets`、`cargo make fast`。

**非目标**：定义任何具体 Runtime 类型。

---

### P1-002：定义受验证的领域标识

**目标**：提供不会与任意字符串混用的稳定标识值对象。

**依赖**：P1-001。

**范围**：先定义阶段内实际需要的 `CorrelationId`；标识内核可复用，但不提前
公开 Capability/Resource/Task ID。

**验收**：

- 非空、长度边界和允许字符规则明确且确定；
- 构造失败返回结构化、可测试的原因；
- 相等、排序、哈希和显示行为一致；
- 类型不暴露可绕过验证的可变内部值。

**测试与验证**：合法、空值、边界、非法字符表驱动测试，`cargo make fast`。

**非目标**：UUID 生成策略、持久化格式、全局注册。

---

### P1-003：定义动态值的标量语义

**目标**：建立协议无关的 `Value` 标量集合和可观察类型分类。

**依赖**：P1-001。

**范围**：`Null`、布尔、整数、浮点和字符串，以及对应 `ValueKind`。整数位宽、
浮点 NaN/Infinity 是否允许必须通过契约和测试明确。

**验收**：

- 每个标量都能无歧义地报告 `ValueKind`；
- 相等语义对所有允许值确定；
- 不依赖 `serde_json::Value` 或具体协议类型；
- 转换 API 不做静默截断或宽松字符串转换。

**测试与验证**：每种标量、数值边界和被拒绝值的测试，`cargo make fast`。

**非目标**：集合、对象、Schema、序列化。

---

### P1-004：扩展动态值的组合语义

**目标**：让 `Value` 表达嵌套列表和字段对象，同时保持确定行为。

**依赖**：P1-003。

**范围**：列表、字符串键对象、只读访问和所有权转换；选择并记录字段迭代顺序。

**验收**：

- 任意受支持标量可递归组成列表和对象；
- 对象重复键的构造行为明确，不发生静默覆盖；
- 查找和迭代不改变值；
- 相等行为不受不明确的哈希迭代顺序影响。

**测试与验证**：嵌套、空集合、重复键和顺序测试，`cargo make fast`。

**非目标**：引用、资源句柄、二进制协议编码。

---

### P1-005：定义精确诊断路径

**目标**：用结构化路径定位嵌套输入错误，而不是拼接临时字符串。

**依赖**：P1-004。

**范围**：字段段、索引段、根路径、追加操作和稳定的人类可读显示，例如
`options.mesh.faces[3].size`。

**验收**：

- 字段和索引不会丢失类型信息；
- 路径追加不修改原路径；
- 空路径、特殊字段名和深层混合路径有确定显示；
- 路径可比较、哈希并作为错误字段公开。

**测试与验证**：显示、追加、相等和特殊字段测试，`cargo make fast`。

**非目标**：JSON Pointer/JSONPath 兼容、自动遍历 `Value`。

---

### P1-006：定义结构化错误核心

**目标**：建立供程序、测试和 Agent 读取的统一错误表示。

**依赖**：P1-004、P1-005。

**范围**：稳定 `ErrorKind`、消息、可选诊断路径、结构化详情和错误来源边界。
`Error` 对外只提供读取与匹配接口；具体错误仅由拥有验证规则的模块在 crate 内部
构造。第一版只包含当前确有语义来源的 invalid identifier、missing field、unknown
field 和 type mismatch 四类；不为尚未出现的 invalid value、Task 或 Resource 失败
预留类别。新类别应与拥有它的实际失败行为、结构化详情和测试一起交付。`Error`
实现标准错误边界，但第一阶段不承诺嵌套 error source 链。

**验收**：

- 调用方可以不解析消息就区分错误类别；
- 嵌套错误携带准确路径；
- 详情使用 Axiom `Value`，不泄露第三方错误类型；
- `Display` 面向人可读，但不是机器判断的唯一依据；
- 公开调用方只能读取错误；拥有规则的内部模块构造错误，且不会接受相互矛盾的
  类别、路径和详情组合。

**测试与验证**：逐类别、带/不带路径、详情和显示测试，`cargo make fast`。

**非目标**：backtrace、日志上报、传输状态码映射。

---

### P1-007：定义最小类型契约描述

**目标**：用运行时可读取的数据描述 `Value` 的预期形状。

**依赖**：P1-004。

**范围**：标量、列表和对象契约；对象字段包含名称、契约和 required 标记。
第一版对象默认严格，不接受未声明字段。

**验收**：

- 契约自身可被安全构造，拒绝重复字段和无效组合；
- 调用方可读取契约用于 Discovery；
- 契约不包含 Rust `TypeId`、泛型实现细节或协议类型；
- 字段顺序确定，便于文档和跨语言一致性测试。

**测试与验证**：合法契约、重复字段、空对象和嵌套契约测试，`cargo make fast`。

**非目标**：union、枚举、默认值、约束表达式、Schema 版本迁移。

---

### P1-008：实现严格契约验证

**目标**：让同一类型契约成为动态输入验证的唯一语义来源。

**依赖**：P1-005、P1-006、P1-007。

**范围**：递归验证标量、列表和对象；报告缺失字段、多余字段和类型不匹配。

**验收**：

- 合法输入成功且不被修改；
- missing、unknown、type mismatch 使用不同 `ErrorKind`；
- 嵌套列表/对象错误返回首个错误的准确路径；
- 不进行字符串转数字、整数转布尔等隐式转换；
- 错误详情至少包含 expected 和 actual 类型信息。

**测试与验证**：成功与三类失败的嵌套表驱动测试，`cargo make fast`。

**非目标**：收集全部错误、默认值注入、数据修复、业务规则验证。

---

### P1-009：定义执行关联上下文

**目标**：提供能显式传播请求与父子操作关系的最小不可变上下文。

**依赖**：P1-002。

**范围**：当前 `CorrelationId`、可选父关联和创建子上下文的显式 API。上下文只
携带关联语义，不充当任意键值依赖容器。

**验收**：

- 根上下文与子上下文关系可无歧义读取；
- 创建子上下文不修改父上下文；
- 不依赖线程本地、全局变量或特定 async runtime；
- 上下文不允许注入任意业务服务或可变状态。

**测试与验证**：根、子、多层传播和不可变性测试，`cargo make fast`。

**非目标**：自动 ID 生成、日志 span、Task 创建、跨进程 header 编码。

---

### P1-010：公共 API 黑盒验证与阶段收口

**目标**：从 crate 外部证明第一阶段原语可以组合，并冻结进入第二阶段的最小契约。

**依赖**：P1-002 至 P1-009。

**范围**：新增 integration tests 和一个 rustdoc 示例，演示构造契约、验证嵌套
`Value`、读取结构化错误以及传播子 Correlation。

**验收**：

- integration test 只使用公开 API；
- 示例同时覆盖成功路径和精确嵌套错误；
- 公共导出最小且命名一致，没有上层占位类型或通用 `Error` 构造器；
- `cargo make full` 通过；
- 阶段范围和实际公开 API 在本文件中保持一致。

**测试与验证**：`cargo test --doc`、`cargo test --test <新增测试名>`、
`cargo make full`。

**非目标**：第二阶段的 Capability 描述或注册表。

## 4. 依赖与建议交付批次

```text
P1-001
 ├─ P1-002 ───────────────── P1-009 ─┐
 └─ P1-003 → P1-004 ─┬─ P1-005 ─┐   │
                      ├─ P1-006 ←┘   │
                      └─ P1-007 ─ P1-008
                                      ↓
                                   P1-010
```

建议按编号顺序交付以减少公开 API 往返调整。P1-002 与 P1-003 在 P1-001 后理论上
可独立推进，但当前仓库规模很小，默认仍由一个连续实现流完成；只有确有并行收益时
才拆分工作区或执行者。

## 5. 第一阶段决策检查点

以下决策必须在对应任务内通过文档和测试落定，不能留给 Adapter 猜测：

1. 标识允许字符、长度和规范化规则；
2. 整数位宽，以及 NaN/Infinity 是否属于 `Value`；
3. 对象字段的存储/迭代顺序与重复键行为；
4. 特殊字段名的诊断路径显示与机器表示；
5. `ErrorKind` 的稳定命名和 expected/actual 详情结构；
6. 严格对象是否默认拒绝未知字段；
7. 验证返回首个错误还是全部错误（第一阶段默认首个错误）；
8. Correlation 的父子关系如何显式表达。

若其中任何决策需要外部协议才能回答，先定义协议无关语义，再把编码选择推迟到
Adapter 阶段。
