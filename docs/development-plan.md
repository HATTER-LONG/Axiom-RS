# Axiom-RS 整体开发规划

## 1. 目标、基线与结论

更新：2026-09-06。依据 [整体设计](Axiom-design.md)，对照 `main / 89b6184`
的源码、公开测试、`architecture.toml` 与 P3 接入记录制定。此次是文档规划，
没有重新运行或宣称通过该代码基线的 Rust 质量门。

最终目标是可嵌入应用的 Capability Runtime：同一套宿主业务能力可以被本地程序、
脚本和 Agent **发现、调用、查询状态、控制持续工作并诊断失败**；对象身份、所有权、
线程亲和和跨入口语义明确。Rust 是首个实现，语言无关通过语义规范和一致性验证实现，
不通过照搬其他语言的类型或内部架构实现。

当前已完成同步能力的技术闭环，尚未完成真实宿主的产品验证，也尚未实现有状态运行时。
后续不能只围绕“补完 P3 MVP”，也不能把全部长期目标压进一次 MVP。路线调整为：
P3 实际接入收口 → P4 资源 → P5 持续任务 → P6 观察 → P7 Agent 入口 →
P8 接入与发布质量 → P9 跨实现验证。阶段编号是默认顺序，实际依赖见第 5 节。

## 2. 代码现状与全目标覆盖

| 设计目标 | 当前证据与限制 | 后续归属 |
| --- | --- | --- |
| 严格动态数据、契约与结构化诊断 | `src/foundation`、`src/contract`；封闭对象表示、有限浮点、字段说明/枚举/范围、结构化路径已实现；尚无资源引用类型 | P4 引用语义；P7 表示映射；P9 规范 |
| 单一权威能力定义与调用 | `src/runtime/mod.rs` 原子保存 descriptor + 实现，校验输入/输出；`CapabilityRegistry` 仍是独立的纯元数据目录，不是执行权威 | P3 实际接入；P8 迁移与使用说明 |
| 嵌入与线程亲和 | Runtime 使用 `Rc`/`RefCell`，`RuntimeHandle` 弱引用支持重入；`Capability` 不要求 Send/Sync；同步调用不捕获宿主 panic | P4 生命周期；P5 宿主驱动任务；P8 关闭行为 |
| 统一动态入口 | `src/command` 仅 list/get/invoke；`axiom-stdio` 提供有界 NDJSON；不是 MCP，也不是并发服务 | P4/P5 增加状态命令；P6 观察入口；P7 第二 Adapter |
| 一次接入、多个调用方 | `lab-inspect` 四个同步计算能力；`e2e.rs` 与 `process.rs` 覆盖跨入口纠错；仅参考宿主 | P3-R01～R04 实际应用验收 |
| 数据与对象身份分离 | Value 只有数据；没有资源目录、租约、失效规则 | P4 |
| Invocation 与持续工作分离 | 没有 Task 身份、状态机、取消、结果留存或宿主工作桥接 | P5 |
| 权威状态查询与观察隔离 | 只有能力快照；没有 Resource/Task 快照、订阅或 Observer | P4/P5 各自查询；P6 观察和聚合 |
| 执行关联 | `ExecutionContext` 显式 root/child；调用链传播已实现，不存放服务 | P5 创建调用到任务；P6 状态变更到诊断 |
| Agent 可理解与纠错 | 严格发现/错误基础已具备；没有实际 Agent 客户端验收 | P7 |
| 接入可维护、可交付 | 参考宿主已有参数漂移测试和维护量记录；README 有按变更选验证的流程 | P8 第二宿主、迁移、性能基线与发布候选 |
| 语言/协议无关 | core 无外部依赖，Adapter 独立 crate；尚无独立规范向量和第二实现 | 各阶段累积向量，P9 规范与第二实现 |

P3 的修复提交 `0f3dc91` 已随 `89b6184` 合入。旧文档中“仍在 feat 分支”和
“参考宿主审查缺口待关闭”的措辞已过期；真实生产宿主仍未选定。代码和测试存在
不等于本次运行过，也不等于真实使用成功。

## 3. 分层与实施约束

现有层次从低到高为 foundation、contract/execution、capability、runtime、command、Adapter；
上层使用已允许的下层公开边界，具体依赖以 `architecture.toml` 为准。
宿主经公开 API 接入，业务领域类型留在宿主。

新增责任按实际实现进入核心，不预先创建占位模块：

| 所有者 | 新增责任与边界 |
| --- | --- |
| foundation | 无业务生命周期的受验证标识/引用值、路径和错误表示；不得反向依赖资源表或任务表 |
| contract | 引用形状/种类和数据契约；不查询对象是否活着，不管理工作状态 |
| resource | 对象身份、存储关系、解析/使用与失效；是资源权威状态源 |
| task | 状态转换、控制、结果/错误留存和快照；是任务权威状态源；不拥有通用调度器 |
| runtime | 协调调用与资源/任务服务；不成为任意服务的全局容器 |
| observation | 订阅与有界通知交付；读取已提交的变化，不替代权威状态、不依赖 command |
| discovery（条件性） | 仅在多源消费者需要时聚合只读快照；不创建另一份可写状态库 |
| command / Adapter | 命令外壳/路由与外部表示；不重新校验宿主业务，不拥有资源和任务状态 |

资源和任务尽量彼此独立。低层不依赖 observation 的具体实现；P6 开始时选定最小
通知接缝，由协调层在状态提交后接出变化，禁止通过循环依赖解决通知。
每次新增模块同时更新架构规则及公开契约；静态检查器的覆盖范围不等于编译器语义证明。

保留当前线程亲和模型。后台工作可以由宿主启动，通过受控结果/状态消息回到所属线程；
不要把 Runtime 改成 Arc<Mutex<_>>，也不要为所有宿主加 Send/Sync。若具体宿主确实
需要其他模型，先在对应任务冻结访问、关闭和重入语义，再实现一个满足该宿主的方案。

## 4. 阶段、里程碑与交付物

| 阶段 | 可交付结果 | 退出条件 | 详细任务 |
| --- | --- | --- | --- |
| P1/P2 已有基础 | 动态原语、契约与元数据发现 | 保留历史验收与回归 | [P1](phase-1-tasks.md)、[P2](phase-2-tasks.md) |
| P3 同步接入 MVP | 一个真实宿主、3～5 个业务能力、本地 + stdio | 实际使用者凭发现和错误完成业务；参考路径不能代验 | [原任务与剩余拆分](phase-3-tasks.md) |
| P4 资源生命周期 | 身份、只读发现、按身份使用、关闭/失效 | 创建/取得 → 查询 → 使用 → 关闭 → 失效诊断跨入口一致 | [P4](phase-4-tasks.md) |
| P5 持续工作 | 宿主驱动任务、状态、进度、取消、结果与回收 | 启动后可继续查询/取消，终态唯一，结果读取不重执行 | [P5](phase-5-tasks.md) |
| P6 观察与状态发现 | 有界订阅、关联诊断、重连恢复、必要聚合 | 慢/失败观察方不改变业务结果，丢事件后可回权威快照 | [P6](phase-6-tasks.md) |
| P7 Agent 使用闭环 | 一个实际需要的第二 Adapter，默认候选 MCP | 实际客户端完成发现、调用、纠错与已支持的状态控制 | [P7](phase-7-tasks.md) |
| P8 可复用 Rust 交付 | 第二宿主接入、必要 helper、关闭行为、性能基线、兼容策略 | 独立宿主可按文档接入，发布候选范围与限制可复现 | [P8](phase-8-tasks.md) |
| P9 跨实现语义 | 版本化规范、一致性向量、独立执行实现验证 | 已声明能力集由两种实现通过同一语义向量 | [P9](phase-9-tasks.md) |

里程碑分开判断：M1=P3 真实同步接入；M2=P4+P5 有状态控制；M3=P6+P7 可观察的
Agent 使用闭环；M4=P8 可复用 Rust 发布候选；M5=P9 跨实现验证。
没有任意一种 Adapter 或模块数量可以代替里程碑验收。版本号在 P8 冻结，不现在承诺 1.0。

## 5. 依赖、优先级与需求缺失时的推进方式

默认先执行 P3-R01（宿主选择）和 P4-001（资源场景与契约）。P3-R01 的场景清单可以
同时为 P4/P5 提供证据；不要求等待 P3 全部结束才开始有依据的状态开发。若真实宿主
必须有资源或 Task，先完成对应状态增量再回到 P3-R04 验收，避免相互等待。

```text
P3 已完成核心 → P3-R01 → P3-R02 → P3-R03 → P3-R04（M1）
                    ├→ P4-001 → P4 实现 → P4 验收 ─┐
                    └→ P5-001 → P5 实现 → P5 验收 ─┴→ M2 → P6 → P7 完整验收（M3）
P3-R01 + 现有 Command → P7-001～004 可先交付同步 Agent 路径
P3-R03 → P8-001 接入反馈；P4/P5/P6/P7 已选范围 → P8 收口（M4）
各阶段可观察契约/fixtures → P9-001～002；P8 稳定候选 → P9 第二实现验证（M5）
```

- P4 与 P5 的基础实现不互为前置；只有“Task 使用资源”的组合任务依赖两者。
- P6 先围绕一个权威状态源实现，资源和任务都完成后再做完整跨源验收。
- P7 同步 Agent 接入可提前，以便早点获取使用反馈；不能因此标记状态控制已实现。
- 没有实际宿主时，继续规范向量整理、现有接入资料整理和状态契约草案。可用明确标记
  的参考状态案例做技术验证，但不能伪造产品验收；具体身份/关闭/调度接口在场景冻结后实现。
- P4/P5/P6 是完整目标中的明确缺口，不再因为计算器“不需要状态”而从路线消失。
  无当前消费方时标记待排期并给出进入条件，不能标为完成。
- Python、CLI、RPC、第二语言实现根据消费方选择；不同时开四套 Adapter。

任务状态见各阶段文件。未实现任务统一标为待开发；“待决策”列出进入实现前必须拿到
的事实。每项任务以一个可评审增量为目标；跨模块配套可以同批交付，不规定一任务一提交。
不在宿主、人员和吞吐未知时给出日历承诺。下一轮排期按依赖逐项拉取；若单项需要同时
冻结多个不稳定接口，先交付该项契约，再按一个行为增量继续拆分，保留父任务链接。

## 7. 验证、完成定义与范围

各任务必须交付实现（或明确的决策产物）、公开行为测试、相关 rustdoc/使用文档以及
真实结果记录。测试保护所属边界的行为，不复制私有布局、调用次数或类型系统保证。
跨入口 fixtures 比较结果、错误类别/路径/详情、关联及状态变化，外壳可以不同。
状态/取消竞态用受控步骤、channel/barrier 和有界等待验证，不依赖 sleep。

验证命令与频率统一遵循 [README](../README.md#development-and-verification)：
文档检查 diff、链接、依赖和状态；局部代码运行受影响测试；最终 Rust 候选执行 full，
其已覆盖 fast。专项工具按具体风险选择，阶段文档不增加额外门禁循环。
涉及路径、进程、线程和关闭行为时保留既有平台支持，并报告实际测试平台。

持续保护 P3 的严格数值表示、帧限制、结构化路径、封闭契约和架构检查回归。
对新行为定义版本/迁移规则；Adapter 不静默截断、转换类型或伪装不支持的能力。
历史运行结果标注候选和日期，不作为新实现的验证结果。

长期仍不属于 core：LLM/Prompt 管理、UI、工作流调度、认证协议、网络服务框架、
数据库持久化、分布式一致性、稳定 C ABI、通用插件热加载。需要这些功能时由宿主或
独立 Adapter 承担；核心只新增实际调用边界必需的语义。
