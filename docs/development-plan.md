# Axiom-RS 整体开发规划

## 1. 规划依据与当前状态

本规划依据 [《Axiom 整体设计》](Axiom-design.md)。Axiom-RS 首先服务于需要将
同一套业务能力开放给本地程序和外部自动化的 Rust 宿主；复杂应用的对象身份、持续
工作和诊断语义是后续价值方向。语言、协议和领域无关是边界原则，不能替代真实宿主验证。

截至 2026-09-05，`main` 的代码基线为 `90d5822`：阶段 1 原语和阶段 2 元数据
注册/发现已落地，阶段 3 尚未开发。当前只能描述、注册、发现和验证，不能调用能力。
审查发现对象契约可通过外部可变模式匹配绕过校验，因此不能宣称阶段 2 的全部
不变量已得到保障；修复纳入阶段 3 的进入门槛。

本次调整是开发计划调整，不代表所列修复或新功能已经完成。历史阶段文档保留原任务
编号；第三阶段文档取代原 Invocation-only 计划，任务编号的迁移在该文档中说明。

## 2. 首个 MVP 与长期成功标准

### 2.1 首个 MVP：真实宿主的发现、调用和纠错闭环

交付一个宿主案例、3～5 个有实际业务意义的同步能力、本地调用入口和一个外部 Adapter。
调用方应能只凭发现结果构造请求，执行真实业务，并根据结构化错误修正请求。

验收必须包括：

1. descriptor 与实现原子注册，发现和执行使用同一份权威契约；
2. 本地与外部调用共享 Runtime 校验和宿主业务实现；
3. 输入错误不执行业务；未知能力、输入错误、业务失败、输出契约违例可区分；
4. 嵌套错误包含路径和结构化详情，执行关联无损传播；
5. 契约封装漏洞已修复，架构检查的已确认漏检有回归保护和明确保障范围；
6. 记录每个能力的契约声明、参数转换和业务接入代码，验证新增入口无需重写业务规则；
7. 示例可从干净环境按 README 运行；一个端到端测试完成发现、错误请求、修正与成功。

默认外部入口为本地 JSON/stdio，协议编码留在 Adapter。若首个真实宿主的验收明确需要
Agent 客户端，则在阶段 3 的需求冻结任务中改选最小 MCP Adapter，并记录选型、版本和
客户端验收方式；首个 MVP 只实现一个 Adapter。

优先接入已有宿主。尚无可用宿主时，可以先做小型工程检查示例，包含真实计算和业务
失败；必须标记为参考宿主，不能将其演示成功等同于真实应用接入验证完成。

### 2.2 后续完整运行时

在 MVP 证明接入价值后，按真实场景逐步支持资源身份与生命周期、Tracked Task、
权威状态发现、观察故障隔离，以及更多 Adapter 和跨实现一致性规范。
这些是长期能力，不要求一次 Invocation 自动具备持久化、取消、事件或资源管理。

## 3. 架构原则

- 强类型业务留在宿主；`Value` 只用于动态边界。
- 契约层拥有形状及已声明约束的验证；宿主拥有业务规则；Command 只验证请求外壳。
- Adapter 负责编码和传输，不重写业务契约、错误类别或对象生命周期。
- descriptor 与实现只有一个权威注册项；不能维护两份可独立漂移的元数据表。
- 调用与持续工作分离，普通数据与对象身份分离，状态权威、事件通知。
- 发现只读、无副作用，返回与后续修改隔离且排序确定的快照。
- 明确所有权、重入和线程亲和；无并发注册需求时不引入注册锁。
- 如有内部同步，解析并捕获所需状态后释放，再执行宿主代码。
- 不为宿主实现预设 `Send + Sync`；跨线程承诺必须来自选定宿主和明确测试。
- 核心保持稳定、safe Rust；不绑定序列化格式、执行器、传输或 LLM。
- 先测量接入重复，再决定是否需要 typed helper；不预先建设宏或泛型适配框架。

## 4. 本阶段模块与后续边界

核心保持单 crate。Adapter 出现实际序列化/协议依赖时，以独立包隔离，核心不能反向
依赖它。示例宿主是使用方，其业务规则不进入核心。拆包用于依赖隔离，不按概念机械拆包。

| 责任 | 阶段 3 的范围 | 依赖方向与边界 |
| --- | --- | --- |
| `foundation` | Value、标识、路径和结构化错误 | 不依赖上层或协议 |
| `contract` | 受验证契约、严格验证、宿主必需的字段说明/约束 | 依赖 foundation |
| `execution` | 显式关联上下文 | 依赖 foundation；不是服务容器 |
| `capability` | 描述、实现边界、业务失败、权威注册责任 | 使用 contract/execution/foundation；不依赖 runtime |
| `runtime` | 注册协调、解析与调用、输入输出验证 | 使用 capability/contract/execution/foundation |
| `command` | 最小发现与调用请求、统一响应 | 使用 runtime 和下层公开类型；不重验业务参数 |
| Adapter | 一个外部编码/传输入口 | 使用 command；核心不依赖 Adapter |
| 宿主案例 | 业务计算与业务状态、Axiom 接入 | 通过公开 API 使用核心；业务与协议转换分离 |

`resource`、`task`、`observation` 尚不创建占位模块。统一 `discovery` 聚合层等多个
权威状态源实际存在后再决定；阶段 3 的发现直接来自可执行注册项。

`architecture.toml` 随已实现边界更新。检查器是有限范围的静态检查，不等价于 Rust
编译器或完整语义依赖证明；其支持和不支持的引用形式必须有文档。

## 5. 已确认问题与处理顺序

| 问题 | 处理要求 | 时点 |
| --- | --- | --- |
| Object 契约可变匹配暴露字段，非法契约可注册 | 在 contract 层封闭表示；覆盖直接构造、可变匹配和嵌套契约 | P3-001，执行 API 前 |
| 架构检查漏检全限定路径引用 | 增加实际复现样例和回归检查，说明解析边界；不自制完整编译器 | P3-002，新增模块前 |
| 强类型参数、契约与 Value 转换可能重复维护 | 真实能力接入记录，加一个参数变更用例；据证据选择最小改进 | P3-003、P3-010 |
| 字段只有名称/类型/required，业务含义不足 | 增加宿主所需字段说明；枚举、单位、范围仅按实际参数引入 | P3-004 |
| 阶段 3 原计划预设跨线程并发 | 先确认宿主线程亲和，冻结一个执行模型并验证重入 | P3-005、P3-008 |
| 工具通过易被误解为契约正确 | 保留门槛，补不变量、端到端与工具回归测试 | 全程 |
| 重复排序、线性查找等局部成本 | 注册责任调整时可顺手消除冗余排序；大对象优化需测量 | 非 MVP 阻塞项 |

## 6. 交付路线

### 阶段 1、2：既有基础与元数据发现

范围和历史任务分别见 [阶段 1](phase-1-tasks.md)、[阶段 2](phase-2-tasks.md)。
保留既有排序、冲突、快照、严格校验和关联语义；已确认的契约漏洞必须先修复。

### 阶段 3：基础修复与首个可用 MVP

详细任务见 [第三阶段开发任务](phase-3-tasks.md)。交付次序为：

```text
修复契约和检查漏检
    ↓
确定宿主、能力清单和外部入口
    ↓
必要的参数语义 + 执行契约
    ↓
原子注册 + 同步调用 + 失败与重入验证
    ↓
最小 Command + 宿主接入 + 一个 Adapter
    ↓
跨入口一致性、纠错闭环和接入成本验收
```

没有可用真实宿主时，继续完成不依赖宿主的修复和核心工作，记录待确认事项；不得通过
缩减宿主验收把阶段标记完成。参考宿主可用于开发测试，真实使用验证仍是单独验收项。

### 阶段 4：由宿主驱动的第一个状态闭环

从资源或 Task 中选择实际需要的一条，先形成独立行为增量：

- 资源：创建/取得身份、查询、使用、关闭或移除、失效诊断；明确是否拥有对象、解析
  是否持有租约、查询是否延长生命周期，以及适用的并发移除语义。
- Task：启动、权威状态查询、取消请求、结果/错误读取；明确终态、取消竞态、结果
  留存和创建调用的关联，重复读取不得重新执行。

选择及原因由阶段 3 的宿主证据决定；另一条在确有需求时独立交付。若宿主在阶段 3
即无法脱离其中一条运行，应先修订该阶段的范围和验收，将最小状态闭环前移，而不是
通过裸字符串假扮受管理资源，或让同步调用假扮可取消任务。

### 阶段 5：必要的观察能力与状态发现

在权威状态存在后加入日志/事件及订阅生命周期，定义快照和订阅衔接。Observer 失败
不得改变业务结果，慢 Observer 不持有核心锁；按需聚合发现。没有消费方时不建通用事件总线。

### 阶段 6：更多入口与跨实现一致性

依据使用需求添加 Python、MCP、CLI 或 RPC，扩展既有 Command 覆盖已实现的状态控制。
从阶段 3 的请求/响应向量开始沉淀一致性测试，再确定跨语言规范、兼容性和第二种实现。
不以实现所有 Adapter 作为发布条件。

原阶段 7 的最小 Command 和阶段 8 的首个 Adapter 已前移到阶段 3；原资源、Task 和
观察计划按上述需求门槛推进，不再要求完成全部基础设施后才能获得第一次外部使用反馈。

## 7. 兼容与验证

- `0.1.x` 阶段边界允许必要 API 调整，但记录迁移方式并同步公开测试和文档。
- 编码格式在 Adapter 定义；首版即明确版本、数值表示、重复键、未知字段、错误路径
  和关联信息。不能用静默转换掩盖核心与外部表示的差异。
- Runtime 原生入口与 Command/Adapter 的响应外壳可不同，核心结果、错误类别、路径、
  详情和宿主所见 context 必须一致。
- 每个代码增量运行 `cargo make fast`，最终候选运行 `cargo make full`，并显式运行
  文档测试和检查脚本测试；引入 Adapter 包时将其相关检查和端到端测试纳入质量工作流。
- 对实际引入的复杂所有权、同步或 unsafe 运行 `cargo make hardening`；更强成功门槛
  覆盖同一未变化状态的较弱检查，不机械重复。
- 不降低覆盖率、不跳过有效诊断、不为新行为新增无依据 exclusion。
- 文档修改检查链接、任务依赖、状态和范围一致性；测试结果注明对应代码与实际执行时间。

## 8. 完成定义

阶段 3 的完成以真实使用和契约测试为准：一个能力只接入一次，两个入口共享行为，
调用方可根据发现和错误完成任务，基础缺陷有回归保护。任务需要同时决定多个不稳定
边界时继续拆分；不得以测试数量、覆盖率或模块数量替代上述产品验收。
