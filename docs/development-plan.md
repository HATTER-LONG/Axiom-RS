# Axiom-RS 整体开发规划

## 1. 规划依据与边界

本规划依据《Axiom 整体设计》需求和当前仓库骨架制定。当前仓库是 Rust 2024
edition 的单 library crate，已具备格式、Clippy、文档、覆盖率、Miri、
AddressSanitizer 和 mutation testing 等质量入口，但业务代码仍是 `add` 示例。

`architecture.toml` 不作为本规划的输入、模块划分依据或需求来源。后续实现若需
调整架构检查配置，应在模块边界稳定后作为独立任务处理，不让现有配置反向决定
领域模型。

项目首先交付一个可嵌入 Rust 应用的 Capability Runtime 核心库。Python、CLI、
MCP、HTTP、RPC 等均是后续 Adapter，不进入核心语义。

## 2. 成功标准

Axiom-RS 的首个完整里程碑应允许宿主应用：

1. 用机器可读契约描述并注册能力；
2. 通过唯一动态入口严格校验并调用能力；
3. 区分普通动态数据、具有身份和生命周期的资源、持续存在的 Task；
4. 无副作用地发现能力、资源和 Task 的权威状态；
5. 获得带精确路径、稳定类别和结构化详情的错误；
6. 在调用、子操作、Task、日志和事件之间传播执行关联；
7. 在观察设施失效时保持业务结果不变；
8. 让 Adapter 只负责表示转换，不改变上述语义。

## 3. 架构原则

- **强类型内部，动态边界外部**：宿主业务保留领域类型；只有跨 Runtime
  边界的数据使用统一动态表达。
- **单一事实来源**：能力决定业务和参数契约，资源系统决定对象存在性，Task
  存储决定任务状态；上层只发现、协调、转换和路由。
- **数据与身份分离**：`Value` 可复制和传输，资源句柄只表示受控身份。
- **调用与持续工作分离**：Invocation 返回值或 Task 身份，但 Invocation 本身
  不等于 Task/Future。
- **状态权威、事件通知**：查询读取快照；事件只宣布变化，不承担状态恢复。
- **观察与控制分离**：Discovery 只读、无副作用；读取结果不得隐式执行。
- **严格动态协议**：未知命令、缺失字段、多余字段、类型不符、目标不存在、
  业务失败和内部失败必须可区分。
- **显式所有权与并发**：核心锁不包围宿主业务代码；公开 API 说明并发、重入、
  取消和销毁语义。
- **Adapter 不反向依赖**：核心不依赖具体协议、序列化格式、执行器或 LLM。
- **安全优先**：稳定 Rust、safe-by-default；只有证明必要时才引入 `unsafe`。

## 4. 目标模块与依赖方向

项目先保持单 crate，以模块形成边界；只有出现独立版本、特性或依赖隔离需求时
才拆分 workspace crate。

```text
adapter (后续独立 crate/feature)
    ↓
command ───────────────→ discovery
    ↓                       ↓
runtime / invocation ─→ capability
    ↓          ↓            ↓
resource     task       contract/schema
    ↓          ↓            ↓
observation / execution context
    ↓
foundation: id, value, path, error
```

依赖箭头表示“使用”。下层不得依赖上层；核心模块不得依赖 Adapter。

| 模块 | 唯一职责 | 明确不负责 |
| --- | --- | --- |
| `foundation` | 标识、动态值、诊断路径、结构化错误 | 注册、执行、协议编码 |
| `contract` | 输入输出类型描述与严格验证 | 能力业务逻辑 |
| `execution` | Invocation/Correlation 上下文及传播 | 全局依赖注入 |
| `capability` | 能力描述、实现边界和注册快照 | Task 生命周期、Adapter |
| `resource` | 身份、存活性、受控解析和只读发现 | 把对象序列化为 `Value` |
| `task` | 权威状态、进度、取消、结果和错误 | 把所有调用异步化 |
| `observation` | 日志/事件观察和故障隔离 | 决定业务成败、保存权威状态 |
| `runtime` | 解析、捕获状态、释放内部锁、调用业务 | 重写能力或资源规则 |
| `discovery` | 无副作用的能力/资源/Task 快照 | 控制或隐式执行 |
| `command` | 严格请求识别、结构验证、路由、统一响应 | 业务规则和传输协议 |
| `adapter` | Rust/Python/CLI/MCP/RPC 表示转换 | 修改核心语义 |

## 5. 交付路线

### 阶段 1：语义基础

建立后续模块共享、但不依赖 Runtime 的最小原语：受验证标识、动态值、诊断
路径、结构化错误、类型契约和执行关联。详细任务见
[第一阶段开发任务](phase-1-tasks.md)。

**退出条件**：类型拥有稳定公开契约、严格边界测试和 API 文档；不包含能力注册、
资源存储、Task、Observer 或协议 Adapter。

### 阶段 2：能力契约与发现

交付能力名称、描述、分类、输入输出契约、只读描述快照和注册冲突规则。先支持
同步、无状态能力，不引入 Task 或 Adapter。

**关键验证**：重复注册、未知能力、确定性列举、快照隔离、契约与调用共享同一
验证来源。

### 阶段 3：Invocation 与 Runtime 调度

建立强类型能力实现边界和统一动态调用路径。Runtime 在锁内只解析并捕获所需
状态，释放锁后执行宿主代码。区分协议/验证错误、业务错误和内部错误。

**关键验证**：参数只验证一次、宿主回调可重入、并发查询安全、业务失败不被
改写、Correlation 正确传播。

### 阶段 4：资源身份与生命周期

提供类型化资源身份、权威存活状态、受控解析和无副作用发现。明确 Runtime 是否
拥有资源，以及弱引用、租约或显式注销中的实际生命周期策略。

**关键验证**：过期和类型不匹配可区分、查询不延长生命周期、并发注销与解析有
确定契约。

### 阶段 5：Tracked Task

引入独立于 Invocation 的 Task 身份、状态机、进度、取消请求、结果和错误。
状态存储是权威来源；事件仅通知变化。

**关键验证**：合法状态转换、终态不可逆、取消竞态、重复读取不重新执行、创建
Invocation 与 Task 的 Correlation 一致。

### 阶段 6：Observability

提供日志和状态变更观察接口、订阅生命周期、快照后订阅策略以及 Observer 故障
隔离。先定义内存内语义，不绑定 exporter 或 tracing 实现。

**关键验证**：Observer panic/错误不改变业务结果、慢 Observer 不持有核心锁、
late subscriber 可先读权威快照。

### 阶段 7：统一 Command Boundary

建立协议无关的 Command/Response 模型，覆盖发现、调用、资源查询、Task 查询和
控制。请求结构严格，未知字段与错误路径可操作；业务仍由下层权威模块决定。

**关键验证**：命令类别完整区分、无模糊 fallback、直接调用和 Command 调用的
核心行为一致。

### 阶段 8：Adapter 与跨实现规范

先选择一个最小 Adapter 验证边界，再按实际需求扩展 Python、CLI、MCP 或 RPC。
同时沉淀语言无关的可观察语义、示例向量和兼容性规则，供未来 C++ 实现复用。

**关键验证**：Adapter 仅转换表示；错误、标识、状态和发现结果有稳定的
conformance tests；不把传输或 LLM 依赖带入核心。

## 6. 版本与兼容策略

- `0.1.x` 期间允许在阶段边界调整未稳定 API，但每次调整必须更新测试和文档。
- 先稳定可观察语义，再承诺序列化格式或 ABI。
- 动态协议加入字段时默认保持严格验证；兼容扩展必须使用明确版本或协商机制，
  不静默忽略未知字段。
- 第三方类型只在 Adapter 内出现，核心 API 使用 Axiom 类型或标准库类型。
- 每个阶段先写行为契约与失败语义，再扩展实现范围。

## 7. 任务交付模板

```text
编号：稳定、可引用的任务 ID
目标：一次交付的单一可观察行为
依赖：开始前必须已完成的任务
范围：允许修改的模块和公开契约
验收：输入/输出/失败行为的客观断言
测试：需要新增或更新的测试层级
验证：实际要运行的仓库命令
非目标：本任务明确不实现的相邻能力
```

一个任务应能在短分支或单个连续工作时段内完成、独立评审、失败时局部回退。
若任务需要同时决定多个公共接口或跨越两个尚未稳定的模块，应继续拆分。

## 8. 全局质量与风险控制

- 每个行为任务同时交付测试和公共文档，不积累“最后补测试/文档”的批次。
- 日常增量运行 `cargo make fast`；最终候选运行 `cargo make full`；涉及 unsafe、
  所有权或并发时增加 `cargo make hardening`。
- 覆盖率是遗漏信号，不替代状态机、竞态、错误路径和属性测试。
- 对 `Value`、Schema、路径和状态机优先用表驱动或属性测试覆盖组合边界。
- 对公开语义建立黑盒 integration tests，避免只验证私有实现。
- 不为未来 Adapter、分布式执行、认证、持久化、工作流或 LLM orchestration
  预留抽象；真实需求出现后再扩展。

| 主要风险 | 控制方式 |
| --- | --- |
| 动态值过早绑定 JSON | 自有 `Value` 语义；序列化留在 Adapter |
| Runtime 变成 God Object | 按权威状态拆分 owner；Runtime 只协调 |
| 所有调用被异步模型污染 | Invocation 与 Task 从类型和阶段上分离 |
| 锁包围宿主代码 | resolve/capture/release/execute 契约与重入测试 |
| Observer 改变业务结果 | 故障隔离并以业务结果测试证明 |
| 错误退化为字符串 | 类别、路径和结构化详情进入契约测试 |
| 多语言实现按源码复制 | 维护语言无关规范和 conformance vectors |
