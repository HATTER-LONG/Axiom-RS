# P6：观察隔离与权威状态发现

## 目标与状态

状态：全部待开发（2026-09-06）。见 [整体规划](development-plan.md) 与
[设计第 11～15 节](Axiom-design.md)。状态始终在 resource/task；通知用于提示变化，
不能成为必须重放的权威数据库。首版只服务一个实际观察消费方，不做通用事件总线。
每项补充公开行为验证和契约文档，按 README 选择验证命令。

## P6-001：冻结观察需求与故障语义

- **依赖**：P4-003 或 P5-002 至少一个实际权威源和一个消费方。
- **交付**：`docs/observation-contract.md`，定义需要的状态通知/日志、关联字段、缓冲上限、丢弃策略、取消订阅、Observer 报错/panic 的隔离边界。
- **范围**：按消费方选择 pull 队列或宿主调度交付；不在业务调用栈同步运行任意慢 Observer。明确 Rust panic=abort 等进程终止无法由运行时恢复的限制。
- **验收**：日志写入失败、队列满、慢消费者、消费方退出均有确定行为；状态成功/失败不因诊断设施改变；故障报告不递归触发同一故障。

## P6-002：有界订阅和解除订阅

- **依赖**：P6-001。
- **交付**：订阅身份、过滤范围、有界队列和取消/释放；更新 observation 架构边界。
- **范围**：实现一种交付机制，限制单订阅缓冲与必要的订阅数量；Observer 不拥有宿主对象/任务生命周期。
- **验收**：解除订阅后无新交付；重复解除行为明确；drop 释放订阅；慢消费者不会无限占内存或阻塞业务，溢出可识别；重入订阅/查询不死锁。

## P6-003：状态变更通知与关联诊断

- **依赖**：P6-002 以及相应 P4/P5 状态转移实现。
- **交付**：状态提交后的通知接缝、需要的日志记录接口；不让低层反向依赖 observation 的具体实现。
- **范围**：只有成功提交才发送变化通知；携带对象/任务身份、revision 或等价排序信息以及相关 context。诊断 payload 不默认为所有业务输入输出的副本。
- **验收**：收到通知时可查询已提交状态；Observer 报错或断开不回滚状态、不改写业务返回；订阅者可以根据创建/操作关联定位任务和错误；核心借用/锁不跨消费方代码。

## P6-004：快照与订阅衔接、断流恢复

- **依赖**：P6-003。
- **交付**：同源快照/通知游标规则、缺口信号和重新取快照步骤。
- **范围**：明确订阅与取快照之间的状态变化如何处理；首版可以允许有标记的重复/缺口，不承诺无限重放或 exactly-once。
- **验收**：订阅前后变化、缓冲溢出、晚订阅和重连均可恢复到权威当前状态；测试主动丢通知再查询，不能靠完整历史事件重建才可用。

## P6-005：多源发现与外部观察入口

- **依赖**：P6-004；完整多源验收依赖 P4-006、P5-007。
- **交付**：资源/任务各自的只读命令复用；仅在消费方需要时增加聚合查询；一个 Command/stdio 可用的有界观察读取路径。
- **范围**：默认考虑显式订阅/拉取通知，保留 NDJSON 一请求一响应；若改推送必须明确版本、帧区分与请求关联。跨源快照默认分别版本化，不伪称全局原子快照。
- **验收**：查询不启动工作、不延长对象寿命；通知不混入协议响应/诊断通道；不支持的订阅模式明确拒绝；聚合结果注明一致性边界，不另存业务状态。

## P6-006：实际观察场景故障验收

- **依赖**：P6-005。
- **交付**：一个任务监控/对象状态消费方、故障注入回归和恢复说明。
- **验收**：启动工作 → 观察进度 → 消费方断开/变慢 → 工作正确完成 → 重连查到终态；成功、业务失败、取消的原始结果与禁用观察时相同。记录缓冲策略、实际事件量和限制；不以“收到了事件”代替故障隔离验收。
